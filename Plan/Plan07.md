# 新任务低 Token 上下文交接方案（Plan07）

## 日期

2026-08-14

## 讨论主题

在当前 Codex 任务上下文过长时，将有效项目状态保存到仓库，使新任务能以更低 Token 消耗继续工作，同时不依赖复制完整聊天历史。

## 目标与背景

项目已经经历多轮架构讨论、实现和验证，当前对话包含大量已经失效或可从代码重建的信息。直接在原任务继续会持续增加上下文成本；复制完整聊天到新任务同样浪费 Token，并可能让旧方案覆盖当前代码事实。目标是保存最小但足够的恢复信息，让新任务从当前事实、决策和未完成事项继续推进。

## 候选方案对比

| 方案 | 核心思路 | 优点 | 缺点与成本 | 风险 | 适用条件 |
|---|---|---|---|---|---|
| 继续使用原长任务 | 保留全部对话上下文 | 无需交接 | Token 持续增长，旧信息和噪声增多 | 模型关注过时结论 | 短期连续工作 |
| 复制完整聊天到新任务 | 人工搬运历史消息 | 信息表面完整 | Token 节省有限，重复大量过程信息 | 关键事实被长文本淹没 | 临时审计完整对话 |
| 仅依赖代码与 Git | 新任务自行扫描仓库 | 事实可靠、无需维护摘要 | 不包含选择理由、当前限制和明确下一步 | 重复探索，可能改变既有边界 | 小型或熟悉的代码库 |
| 仓库级 HANDOFF + 分层读取 | 用短文档保存状态索引，代码、测试、Plan 和 Git 作为事实源 | Token 少、恢复快、可审查、可版本化 | 阶段变化后需要更新 | 交接文件过期会误导新任务 | 当前项目，已选择 |

## 最终选择

在仓库根目录创建 `HANDOFF.md`。文件只记录项目目标、当前默认 Workflow、已完成能力、关键设计决策、已知限制、下一步、关键文件、验证命令、Git 基线和安全提醒。新任务先读取 HANDOFF，再按需读取关键代码；代码、测试和 Git 始终优先于交接摘要。

## 选择理由

- 将对话过程压缩成可操作状态，避免重复传递大量历史消息。
- 使用仓库文件可版本化、可审查，也能随代码一起迁移。
- 将“状态索引”和“事实来源”分开：HANDOFF 指路，代码和测试裁决。
- Plan 保存策略原因，track 保存每日事实，Git 保存实现历史，无需在 HANDOFF 重复全部内容。
- 新任务可以采用渐进读取，只在修改某个模块时加载对应文件。

放弃继续使用原长任务和复制完整聊天，是因为无法明显降低 Token；不选择只依赖代码，是因为新任务仍会重复理解设计意图和优先级。

## 架构或流程

```text
旧任务阶段结束
  → 更新 HANDOFF 当前状态
  → 代码 / 测试 / Git 保持权威事实
  → 新任务读取 HANDOFF
  → 检查 git status 和最近提交
  → 按下一步只读取相关关键文件
  → 必要时查询 Plan 和 track
  → 继续实现
```

## 执行步骤

1. 在仓库根目录创建 `HANDOFF.md`。
2. 写入项目目标和当前默认 DAG Workflow。
3. 汇总已完成能力、关键边界和明确限制。
4. 给出按优先级排序的下一步。
5. 列出关键代码、设计文档和验证命令。
6. 记录 Git 基线和不得提交的敏感、运行时文件。
7. 提供新任务可直接使用的简短开场指令。

## 约束与风险

- HANDOFF 不能包含 `.env`、API Key、凭据或模型原始推理。
- HANDOFF 不是运行时 Memory，也不替代代码、测试、Git 或 Plan。
- 交接摘要可能随着实现变化过期，新任务必须先检查工作区和代码。
- 不应把大段源码、完整聊天或所有历史方案复制进交接文件。
- 多个任务并发修改仓库时，HANDOFF 只能描述已确认状态，不能代替冲突检查。

## 待验证事项

- 新任务只读取 HANDOFF 和关键文件后，能否正确复述当前架构和继续下一步。
- 与继续使用长任务相比，实际输入 Token 和重复探索时间降低多少。
- HANDOFF 应按每次阶段完成更新，还是由每日归档自动检查更新。
- 如何检测 HANDOFF 的 Git 基线或关键描述已经过期。
