# 事故学习闭环覆盖范围

> 闭环主计划位于 [`Plan/Plan25.md`](./Plan25.md)，文件名称为《Plan25：事故学习闭环一等子系统》。本文用于说明该闭环可以发现哪些错误、当前覆盖到什么程度，以及如何衡量漏检概率。

## 1. 结论

目前不能声称闭环能够发现某个固定百分比的生产错误。

原因是事故学习闭环本身不是单一错误检测器，而是连接以下能力的生产控制链：

```text
Runtime Event
→ Detector / Invariant
→ Incident Ledger
→ 止损与证据封存
→ RCA 与 Replay
→ ChangeSet 验证
→ Guardrail / Regression / Policy / Runbook
→ 持续统计命中、漏检、误报和复发
```

实际发现能力取决于事件是否可观测、是否存在对应 Detector、是否有事实判定依据，以及是否能在造成用户影响前完成止损。

当前状态是“已规划、未实现”，因此：

- 当前新增的自动发现能力为 `0`；
- 故障演练目录已规划 `36` 个代表性故障机制；
- `INC-02` 首批计划实现 `6` 个明确 Detector：
  - `false_completed`；
  - `stale_verification`；
  - `workspace_drift`；
  - `stuck_cancelling`；
  - `budget_overrun`；
  - `duplicate_side_effect`。

这里的 `36` 表示已经进入故障目录的代表性失效机制，并不表示系统只可能出现 36 个 Bug，也不代表这些故障已经被系统自动检测。

## 2. 不同错误类型的覆盖能力

| 错误类型 | 预期发现能力 | 主要依据 | 主要盲区 |
|---|---|---|---|
| 非法状态转换、越权、预算突破、重复副作用 | 很强 | 确定性状态机、权限和幂等不变量 | 未接入统一 Runtime 边界的旁路执行 |
| Provider 超时、非法 Schema、空响应、Usage 异常 | 较强 | Adapter 契约、协议校验、超时和指标 | Provider 静默语义漂移、错误分类不完整 |
| 取消、恢复、迟到结果等并发竞态 | 中等 | Event Journal、幂等键、故障注入和状态机测试 | 稀有时序、跨进程和跨资源组合竞态 |
| Context 丢失、过期事实、错误检索 | 中等偏弱 | Provenance、版本、ACL、标准检索评测集 | 没有标准答案的相关性和时效性错误 |
| 模型结果看似合理但事实或业务结论错误 | 较弱 | 独立 Validator、业务规则、外部事实证据 | 无事实判定器、开放域问题和主观质量问题 |
| 从未出现过的新型组合故障 | 无法预先估计 | 异常检测、人工审计、用户反馈、Game Day | Unknown unknown 和多个控制层的相关性失效 |

因此，该闭环最适合发现并消除的是：

> Harness 本应确定性保证，但由于契约、状态机、权限、持久化、并发、验证或 Adapter 缺陷而没有保证的错误。

它不能替代领域 Validator，也无法仅凭多 Agent 自我讨论保证所有模型输出都正确。

## 3. 必须区分的三种覆盖率

### 3.1 故障目录覆盖率

衡量已经识别的故障机制中，有多少存在检测器和演练用例：

```text
故障目录覆盖率
= 已有 Detector 和测试的故障机制数
  / 已登记的故障机制总数
```

该指标只能说明已知故障的工程覆盖情况，不能推断未知故障数量。

### 3.2 检测漏网率

衡量故障已经发生后，系统是否发现：

```text
检测漏网率
= 未被任何检测器发现的故障注入次数
  / 实际故障注入次数
```

### 3.3 影响漏网率

衡量系统虽然可能最终发现了故障，但是否在止损前已经影响用户：

```text
影响漏网率
= 在止损前已经造成用户影响的故障注入次数
  / 实际故障注入次数
```

“事后检测到”不能算作成功阻止，因此检测覆盖率和影响覆盖率必须分别统计。

## 4. 漏网概率模型

对于某一类故障，可以将影响漏网概率表达为：

```text
P(影响漏网)
= 1 - P(故障可观测)
      × P(检测到 | 可观测)
      × P(成功记录和告警 | 已检测到)
      × P(在造成影响前止损 | 已告警)
```

这个模型揭示了四类独立的工程问题：

1. **可观测性缺口**：错误没有产生可信事件，或者绕过了统一执行边界；
2. **检测缺口**：存在事件，但没有 Detector，或 Detector 条件不完整；
3. **控制链缺口**：Detector 命中，但 Journal、告警、Incident Ledger 或值班链路失败；
4. **止损时效缺口**：系统最终发现了事故，但发现或响应太晚。

因此，即使单个 Detector 的测试准确率达到 99%，也不能直接声称系统影响漏网率只有 1%。

## 5. 如何得到有统计意义的漏检数字

如果对同一故障族进行了 `N` 次具有代表性、近似独立的故障注入，并且没有出现漏检，可以使用“零失败三倍法则”估计其 95% 置信水平下的漏检率上界：

```text
漏检率的 95% 上界 ≈ 3 / N
```

| 代表性实验数 | 零漏检时可支持的漏检率上界 |
|---:|---:|
| 36 | 约 8.3% |
| 300 | 约 1% |
| 3,000 | 约 0.1% |
| 30,000 | 约 0.01% |

例如，36 个故障机制各演练一次且全部被发现，只能说明观察结果为 `36/36`，不能证明生产漏检率接近于零。在样本具有代表性的前提下，其总体漏检率上界仍可能约为 8.3%。

反复执行完全相同的测试不能简单当作大量独立证据。有效实验至少需要覆盖：

- 不同故障机制；
- 不同状态和中断位置；
- 不同 Provider、Model 和 Adapter；
- 不同并发时序和恢复顺序；
- 不同任务规模和上下文长度；
- 不同 Harness、Prompt、Policy 和 Schema 版本；
- 事故用例与正常路径对照。

一旦出现漏检，应使用二项分布置信区间等方法计算范围，而不是只报告一个原始百分比。

## 6. 主要漏网来源

即使闭环全部实现，仍然会存在以下漏网来源：

1. 执行路径绕过 Harness 或统一事件入口；
2. 事件存在，但缺少对应的 Detector；
3. Detector、Reviewer 和执行 Agent 依赖同一个错误事实源；
4. 故障只有在多个模型、工具和状态组合下才出现；
5. 语义结果没有标准答案或独立验证器；
6. 新模型或 Provider 静默更新后发生行为漂移；
7. 检测器命中，但告警、存储或止损链路失败；
8. 用户影响发生在系统能够检测之前；
9. 采样、日志裁剪或脱敏错误删除了关键证据；
10. 从未被故障目录、测试、审计或用户反馈揭示的 unknown unknown。

尤其需要避免让同一个模型同时生成结果、审查结果并判断事故是否关闭。相关性失效会让表面上的多层检测同时漏掉同一个问题。

## 7. 建议的阶段性目标

第一阶段不设置一个笼统的“全系统漏检率”，而是按故障族、严重等级和版本分别统计。

### SEV0 / SEV1 已知硬不变量

- 故障目录用例检测率必须为 100%；
- `false completed`、跨边界污染、越权副作用、重复不可逆副作用目标值为 0；
- 每条控制必须同时具有负向事故用例和合法路径对照；
- 任何漏检都必须重新打开 Incident，并阻止对应 Guardrail 晋升或继续发布；
- 测试集 100% 通过只能证明已知样本，没有资格宣称生产绝对零风险。

### SEV2 / SEV3 运行故障

- 分别统计每个 Provider、Adapter 和模型版本的检测率；
- 通过 Shadow 收集误报和漏报，再决定是否 Active；
- 同时衡量 MTTD、MTTC 和用户影响，而不只衡量是否最终记录 Incident。

### 语义与质量故障

- 建立领域任务集、标准证据和独立 Validator；
- 分任务类型计算 accepted rate、事实错误率和人工纠正率；
- 不把状态机与权限规则的高检测率外推到开放域语义正确性；
- 无法验证时保持 `unknown`，不能转换为 `passed`。

## 8. 建议新增的覆盖台账

事故子系统实现后，建议为每条 DetectionRule 维护可查询的覆盖记录：

```text
DetectionCoverage
  rule_id
  rule_version
  fault_family
  harness_version
  provider
  model
  adapter_version
  injected_count
  detected_count
  pre_impact_contained_count
  missed_count
  escaped_count
  false_positive_count
  confidence_interval
  last_validated_at
```

这样系统才能回答：

> 对哪类错误、在哪个版本、经过多少次代表性实验、检测率是多少、漏检率置信上界是多少，以及仍有哪些故障没有 Detector 覆盖。

## 9. 当前可以做出的准确表述

当前项目可以准确陈述为：

> 事故学习闭环已经规划 36 个代表性故障机制，首批将实现 6 类高价值 Harness Detector。由于系统尚未进入 `INC-01/INC-02` 实现和 Shadow 数据收集阶段，目前没有可用于声明生产漏检率的实测数据。后续应通过分故障族的故障注入、正常路径对照、Shadow、Canary 和线上 escaped incident 统计，逐步建立覆盖率及其置信区间。

闭环的目标不是宣称“不会有漏网之鱼”，而是让每次漏网都能够被识别、重放、归因并转化成更强的回归测试、不变量、Policy、Guardrail 或 Runbook，使相同失效机制越来越难再次造成用户影响。
